# FactoryTalk Optix — working notes for this folder

This folder holds hand-authored FactoryTalk Optix Studio projects (no Studio was
used to generate them). Everything here was learned the hard way; read it before
editing any `.optix` project so the expensive mistakes don't repeat.

## Projects here
- `optix/` (base) — **ValveProving**: Honeywell 7800 SERIES valve proving, Siemens
  SKP15/SKP25 gas train. Tags: `VP1`, `VP2`, `VPS` (TRUE = test fail), `Pilot`,
  `Lockout` (output).
- `optix/valve proving with low and high gas pressure switch/` — **ValveProvingGasPressure**:
  the base project plus inlet gauge and supervised `LGP`/`HGP` gas-pressure switches,
  adjustable `LGPSetpoint`/`HGPSetpoint`/`VPSSetpoint`, `SupplyPressure`/`DownstreamPressure`.

The two projects are independent Studio projects (own GUIDs). All screen animation
and the proving sequence live in `ProjectFiles/NetSolution/ValveProvingLogic.cs`,
which drives widgets **by name** — keep widget names stable and the logic reconnects.

## On-disk project format (verified against Rockwell docs + official samples)
- Root: `<Name>.optix` and `<Name>.optix.design` (YAML). The `.optix` lists module
  dependencies + `Nodes: - File: Nodes/<Name>.yaml`.
- `Nodes/<Name>.yaml` is the project root (`Type: ProjectFolder`) and `- File:`
  includes each category folder: `UI`, `Model`, `Alarms`, `Converters`, `Recipes`,
  `Loggers`, `DataStores`, `Reports`, `OPC-UA`, `CommDrivers`, `NetLogic`,
  `Security` (Users/Groups/Roles), `System`, `Translations`, `Retentivity`.
- `ProjectFiles/NetSolution/`: `<Name>.csproj`, `<Name>.sln`, the `.cs` NetLogic.
  `<Name>.references` and `bin/ obj/ .vs/` are regenerated by Studio → gitignored.
- Nodes may carry `Id: g=<32 hex>`. When **copying** a project: regenerate the
  project GUID (in `.optix`), every node `Id`, and the `.sln` project GUID, and
  rewrite all `/Objects/<OldName>/...` paths to the new project name. GUID
  collisions between two projects in the same repo cause trouble.

## Widget + datatype gotchas — these caused real runtime crashes
The pattern every time: a widget property was serialized with the wrong `DataType`,
so the widget's own getter/setter threw `InvalidCastException` **every 100 ms scan**,
which floods the log and makes the whole screen look frozen / every button dead.

- **Label / Button `Text` is `LocalizedText`, not `String`.** In YAML use
  `DataType: LocalizedText` with `Value: {"LocaleId":"en-US","Text":"..."}`. From
  NetLogic, never assign a raw string — use the typed property:
  `widget.LocalizedText = new LocalizedText(string.Empty, text, "en-US");`
  (this is the exact form Rockwell's own template logic uses). Assigning a string
  throws `Unable to cast System.String to UAManagedCore.LocalizedText`.
- **TextBox `Text` is also `LocalizedText`** — same crash if declared `String`.
  For numeric entry, don't use a TextBox at all (see next).
- **SpinBox is the right widget for numeric setpoints.** It gives numeric-only
  input (numeric keypad, no letters) and enforces `MinValue`/`MaxValue`. Its
  `Value`, `MinValue`, `MaxValue` must be **`DataType: Double`** (NOT Float — Float
  crashes the same way). Read/write it as `(float)box.Value` / `box.Value = ...`.
- **CircularGauge is draggable by default.** Set `Editable: false` (Boolean,
  Optional) to make it a read-only display. `Value` is `Float`. Only leave the one
  gauge the operator is meant to adjust as `Editable` (or unset).
- Shapes: `Rectangle`/`Ellipse` use `FillColor` (Color); `PolyLine` uses a `Path`
  string plus `FillColor`/`LineColor`. Colors are `"#rrggbb"` in YAML; in C#
  `new Color(0xAARRGGBBu)`.

## NetLogic patterns
- Resolve tags with `Project.Current.GetVariable("Model/X")`, widgets with
  `Owner.Get<T>("WidgetName")`. Button clicks call `[ExportMethod] public void`
  methods, wired in UI.yaml via an EventHandler → MethodContainer whose
  `DynamicLink` points at `.../ValveProvingLogic@NodeId`.
- The NetLogic node in UI.yaml must **declare** each method as
  `- Class: Method / Name: X` for every `[ExportMethod]`.
- Drive periodic animation with `new PeriodicTask(Tick, 100, LogicObject)`.
- **Always** wrap `Start()` in try/catch that logs `ex.ToString()` and rethrows,
  and log a `BUILD vN started OK` marker at the end of Start(). If Start() throws,
  every control the logic wires goes dead — the marker + full stack trace is how
  you tell a real bug from a stale compiled assembly.

## Debugging
- The runtime log is `FTOptixRuntime.log`. A **rising** error count = an exception
  thrown every scan; the stack trace names the throwing widget/line exactly (e.g.
  `FTOptix.UI.TextBox.get_Text()` pointed straight at a mis-typed Text variable).
- **Stale DLL:** if the new `.cs` fails to compile, Studio keeps running the old
  assembly, so the *same* error persists after a "fix." Confirm the running build
  via the `BUILD vN` marker; if it's old, close Studio, delete `bin/ obj/ .vs/`,
  reopen, rebuild. Bump the marker version on each substantive logic change.
- Gauges/labels only update at **runtime** (Play/emulator). The designer shows
  static default values — a gauge "stuck" at its default is usually just design mode.

## Before every push — validate (all previously caught real breakage)
Run a quick script that asserts:
1. every `Nodes/**/*.yaml` + `*.optix*` parses as YAML;
2. every `Owner.Get<T>("Name")` in the `.cs` exists as a widget in `UI.yaml`;
3. every `GetVariable("Model/X")` exists in `Model.yaml`;
4. every button-wired method == an `[ExportMethod]` == a declared NetLogic method;
5. C# braces balanced; no raw `<widget>.Text = "..."` string writes remain;
6. for a copied project: no GUID collisions with the sibling project, and no
   `/Objects/<OtherProjectName>/` paths leaked in.
